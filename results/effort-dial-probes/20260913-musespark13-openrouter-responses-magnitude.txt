Is OpenRouter's effort dial inert for Muse Spark 1.3? NO - AND A PUBLISHED ROW SAID IT WAS - 2026-09-13

VERDICT: THE DIAL WORKS ON THE SURFACE THE HARNESS ACTUALLY USES, AND FOUR EARLIER RECEIPTS MISSED
IT BECAUSE THEY PROBED A DIFFERENT SURFACE. This board published Muse Spark 1.3 / Muse Code /
OpenRouter as effort=default, effort_status=inert_default, on the strength of four receipts at up to
n=9. Every one of them probed https://openrouter.ai/api/v1/MESSAGES with a flat top-level
`reasoning_effort`. Muse Code does not use that surface. It speaks the RESPONSES API, and the shim
in the path forwards to https://openrouter.ai/api/v1/RESPONSES touching only the model id, the
provider pin and the stream flag. On that surface, with the nested `reasoning:{effort}` object the
harness actually sends, the dial is not inert at all.

THE MAGNITUDE READING. Worst within-tier spread is 1.46x (minimal). Bottom-to-top ratio of means is
13243/845 = 15.7x, which clears it ten times over. The bands are very nearly a clean staircase:
minimal, low, medium and high are mutually disjoint, and the only overlaps anywhere are two narrow
ones at the top boundaries (high tops out at 8573 against xhigh's floor of 8491; xhigh tops out at
12264 against max's floor of 12112). This is a BETTER BEHAVED DIAL THAN META'S OWN ENDPOINT, where
high, xhigh and max overlap almost entirely and one max call thought less than two high calls.

Read that pair carefully: the two routes agree closely on what each tier COSTS in thinking, which is
itself evidence that nothing is being dropped or rewritten in transit. What differs is the top end,
where the aggregator separates and the first-party endpoint does not - at n=3, on one prompt, so
that difference is noted and not claimed.

AND HERE IS THE PART THAT CHANGES A PUBLISHED ROW. The arm ran with NO --reasoning-effort flag, and
an unflagged Muse Code does not omit the field. Captured at the request body:

    muse exec ... (no --reasoning-effort at all)
      call 1  MAIN LOOP  reasoning.effort = "high"
      call 2  observer   reasoning.effort = "low"
      call 3  observer   reasoning.effort = "minimal"
      call 4  observer   reasoning.effort = "high"

So the main loop asserted `high`, the shim forwarded it untouched, and the route applied it. The
published row did not run at "the provider default" - the route's own default is MEDIUM, per the
omitted-field control above, and the row never used it. THE ROW RAN AT high. Its effort label is
being corrected from default/inert_default to high/verified.

WHY THIS HAPPENED, AND IT IS THE SECOND TIME. On 2026-09-12 a probe of GLM-5.3 Flash sent Z.ai's own
DOCUMENTED field name (`reasoning_effort`) instead of the one Claude Code puts on the wire
(`output_config.effort`), got HTTP 200 on an invented tier, and would have published a validated
dial as inert. That one was caught before publication and its receipt made the near-miss the
headline. This is the same error - probe the surface and the field THE HARNESS USES, not the one the
vendor documents or the one a previous probe happened to use - and this time it shipped, and sat on
the public board for a day. The rule now has a code path rather than a paragraph: a wire tap that
records what a harness actually sends is a standing instrument here, and asserting a tier requires
running it first.

WHAT THIS RECEIPT DOES NOT SHOW. Thinking volume is not quality, and nothing here says the extra
tokens buy better bug-finding. It is one prompt at n=3 per tier. It also does not retroactively
validate the four /messages receipts: on THAT surface the flat field really did produce overlapping
distributions at n=9, and that finding stands for that surface. Both things are true, which is the
whole point - a dial is a property of a serving path, and a serving path includes which API you call.
